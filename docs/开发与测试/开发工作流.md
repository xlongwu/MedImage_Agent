# Agent 开发工作流 (DEVELOPMENT_WORKFLOW)

本文档说明如何用 **Codex / Claude Code** 等代码 Agent 安全、高效地开发 MedImage Agent。

---

## 1. 前置条件

在开始任何开发任务前，确保：

1. 已阅读 `AGENTS.md`（了解项目架构和禁止事项）
2. 已阅读 `docs/安全与审批/安全边界.md`（了解安全边界）
3. 已阅读 `docs/ARCHITECTURE.md`（了解各层职责）
4. 当前分支干净（`git status` 无未提交变更）
5. 依赖已安装（`pip install -r requirements.txt && cd src/frontend && npm install`）

---

## 2. Task Packet 格式

每次开发任务应打包为以下格式（由人或 Agent 编写）：

```markdown
## Task Packet: <简短标题>

### 目标
<1-2 句话描述要达成什么>

### 背景
<为什么需要这个改动>

### 范围
- 修改的文件：（列出）
- 不改的文件：（列出）

### 约束
- 不修改 rawdata
- 不绕过 approval gate
- <其他任务特定约束>

### 验收标准
- [ ] <标准 1>
- [ ] <标准 2>

### 测试命令
- <pytest 命令>
```

任务交接应直接遵循本模板和 `AGENTS.md` 的完整交接字段；已完成的历史任务
不得继续作为当前实现依据。

## 3. 开发循环：Plan → Implement → Review → Test

### 3.1 Plan（规划）

Agent 在动手前必须先阅读相关代码，然后提交计划：

- **小改动**（单文件、<50 行）：口头说明即可
- **中型改动**（2-3 文件、<200 行）：简要说明修改方案
- **大型改动**（多文件、架构调整）：必须使用 `submit_plan` 提交结构化计划，等待用户确认

计划必须包含：
- 改什么文件
- 每个文件的改动内容
- 不改什么（明确排除）
- 风险点

### 3.2 Implement（实现）

实现阶段：

1. 先读文件（`read_file`），确认当前内容
2. 使用 `edit_file` 或 `multi_edit` 进行修改
3. 每次修改聚焦一个目标
4. 修改后立即说明改了什么

### 3.3 Review（审查）

提交 PR 前的自查：

```bash
# 查看 diff
git diff

# 检查是否有意外改动
git diff --stat

# 确认没有敏感信息
git diff | grep -i "api.key\|password\|secret\|token"
```

也可以使用 `review` 或 `security_review` 子代理进行自动审查。

### 3.4 Test（测试）

```bash
# 全量测试
pytest

# 如果全量太慢，至少运行相关的测试文件
pytest tests/unit/test_<相关模块>.py -v

# 如果修改了 API，运行 API 测试
pytest tests/api/ -v

# 如果修改了前端，运行类型检查
cd src/frontend && npm run typecheck
```

## 4. 如何 Review Diff

### 4.1 人工 Review 清单

- [ ] 是否有对 rawdata 目录的写入操作
- [ ] 是否有绕过 approval gate 的代码路径
- [ ] 是否有硬编码的 API key 或私密路径
- [ ] 是否有前端直接操作文件系统的代码
- [ ] 是否有 LLM 直接调用工具的代码
- [ ] 新代码是否包含测试
- [ ] 新 pipeline node 是否有对应的 pipeline YAML
- [ ] 文档是否需要更新

### 4.2 自动 Review

```
# 让 Codex 审查 diff
/review "focus on safety boundaries and approval gate"

# 安全专项审查
/security_review "focus on file operations and input validation"
```

## 5. 如何运行测试

### 5.1 后端测试

```bash
# 全量
pytest

# 单元测试
pytest tests/unit/

# 单个测试文件
pytest tests/unit/test_motion_qc.py -v

# 匹配测试名称
pytest -k "test_motion" -v

# 含覆盖率
pytest --cov=src/backend --cov-report=term-missing

# 集成测试
pytest tests/integration/

# API 测试（需要后端启动）
pytest tests/api/
```

### 5.2 前端测试

**任何前端改动必须本地运行 `npm run build` 通过才能提交。**

```bash
# 构建检查（必须通过）
cd src/frontend && npm run build

# 类型检查
cd src/frontend && npm run typecheck

# Lint
cd src/frontend && npm run lint

# 格式化检查
cd src/frontend && npm run format:check
```

手动 smoke checklist 见 [`docs/桌面与前端/前端冒烟检查.md`](../桌面与前端/前端冒烟检查.md)。

### 5.3 启动验证

```bash
# 后端健康检查
curl http://127.0.0.1:8000/health

# 前端可访问
curl http://127.0.0.1:5173
```

## 6. 如何更新文档

### 6.1 ROADMAP.md

当完成一个里程碑时更新：
- 将对应阶段的状态从 🔄 改为 ✅
- 在交付物列表中勾选已完成项

### 6.2 TASK_BACKLOG.md

当创建、完成或放弃任务时更新：
- 新任务：添加条目，分配 task_id
- 完成任务：标记 `status: ✅ 已完成`，记录完成日期
- 放弃任务：标记 `status: ❌ 已放弃`，记录原因

### 6.3 DECISIONS（架构决策记录）

当做出影响架构的重大决策时：
- 在 `docs/架构与决策/决策记录/` 中创建新文件（编号递增）
- 格式遵循：状态 → 上下文 → 决策 → 后果

### 6.4 ARCHITECTURE.md

当组件状态发生变化时更新：
- "当前状态 vs 目标状态" 对照表
- 新增或删除组件

## 7. 大任务拆分规则

### 7.1 何时拆分

当任务满足以下任一条件时，应该拆分：

- 涉及超过 3 个模块
- 预计变更超过 200 行
- 同时涉及前端和后端
- 需要先设计再实现
- 有外部依赖（如 MATLAB 环境、GPU）

### 7.2 如何拆分

遵循以下原则：

1. **按层拆分**：后端逻辑和前端 UI 分开
2. **按依赖拆分**：先完成被依赖的部分（如 Tool Catalog 先于 Pipeline Executor 集成）
3. **每个子任务可独立测试**：每个拆分后的任务有独立的验收标准和测试命令
4. **每个子任务一个 PR**：便于审查和回滚

### 7.3 示例：T-0012 的拆分

原始任务「在 pipeline_executor 中集成权限检查」拆分为：

```
子任务 1：扩展 tool_registry.py 定义所有工具权限
子任务 2：在 pipeline_executor.py 中添加 assert_tool_allowed 调用
子任务 3：添加单元测试
子任务 4：添加集成测试
```

## 8. 并行 vs 串行规则

### 8.1 可以并行的任务

- 纯文档修改
- 不同模块的独立单元测试
- 前端组件开发（不依赖后端改动）
- 后端工具开发（不依赖前端改动）

### 8.2 必须串行的任务

- 设计 → 实现（先设计后实现）
- 后端 API → 前端对接（先定义 API 再实现前端）
- 核心模块修改 → 集成测试（先改再测）
- Tool Registry → Pipeline Executor 集成（先注册再调用）

### 8.3 依赖关系速查

```
M1（文档建设）          ← 可并行
  ↓
M2（Tool Catalog）      ← 依赖 M1
  ↓
M3（Plan Validator）    ← 依赖 M2
  ↓
M4（LLM Planner）       ← 依赖 M3
  ↓
M5（GUI Agent）         ← 依赖 M4
  ↓
M6（Plan Review UI）    ← 依赖 M5
  ↓
M7（真实数据沙箱）      ← 依赖 M6
```

M6 和 M7 中的纯前端任务可以与 M5 的后端任务部分并行。

## 9. CI（持续集成）

### 9.1 CI 触发条件

- 推送到 `main`、`master`、`develop` 分支
- 创建 PR 到 `main`、`master`、`develop`

### 9.2 CI 内容

| Job | 环境 | 命令 |
|-----|------|------|
| backend | Python 3.11 | `pip install -r requirements.txt` → `pytest --tb=short` |
| frontend | Node 20 | `npm ci` → `npm run build` |

### 9.3 本地模拟

```bash
# 模拟 backend CI
pip install -r requirements.txt
pytest --tb=short

# 模拟 frontend CI
cd src/frontend
npm ci
npm run build
```

### 9.4 CI 限制

- 不安装 MATLAB/SPM/DPABI/GPU/CuPy
- 不运行真实医学影像预处理 pipeline
- GPU 相关测试自动 skip

## 10. 完整示例：一个 task packet 的开发过程

### Task Packet

```markdown
## Task Packet: 添加新的 QC 指标模块

### 目标
为 Motion QC 添加 mean FD 的组水平统计

### 背景
当前 `motion_qc.py` 只有 per-subject 的 FD 计算，没有组水平汇总

### 范围
- 修改：`src/backend/app/tools/motion_qc.py`（添加组汇总函数）
- 修改：`src/backend/app/runtime/node_registry.py`（注册新节点）
- 新增：`examples/pipeline_motion_qc_group.yaml`
- 新增：`tests/unit/test_motion_qc_group.py`

### 约束
- 不修改 rawdata
- 只读取 `outputs/derivatives/` 中的数据
- 写入 `outputs/reports/`

### 验收标准
- [ ] `write_motion_qc_group_report()` 生成组水平 CSV 和 MD 报告
- [ ] 新节点 `motion_qc_group_report` 可通过 pipeline 执行
- [ ] 单元测试覆盖至少 2 个受试者的场景

### 测试命令
- `pytest tests/unit/test_motion_qc_group.py -v`
- `pytest tests/unit/test_motion_qc.py -v`（回归）
```

### 开发过程

```
Step 1: Agent 阅读 motion_qc.py 和 node_registry.py
Step 2: Agent 提交计划（口头或 submit_plan）
Step 3: 用户确认
Step 4: Agent 实现代码
Step 5: Agent 运行测试并报告结果
Step 6: Agent 更新 TASK_BACKLOG.md 标记任务完成
```

### Agent 的最终报告

```
## 改动摘要

### 修改的文件
- src/backend/app/tools/motion_qc.py：添加 write_motion_qc_group_report()
- src/backend/app/runtime/node_registry.py：注册 motion_qc_group_report 节点
- examples/pipeline_motion_qc_group.yaml：新建 pipeline 配置

### 新增的文件
- tests/unit/test_motion_qc_group.py：5 个测试用例

### 测试结果
- pytest tests/unit/test_motion_qc_group.py -v：5 passed
- pytest tests/unit/test_motion_qc.py -v：12 passed（回归）
- pytest：138 passed, 0 failed

### 风险
- 组水平报告假设所有受试者的 FD 文件格式一致，未处理格式不一致的情况
- 需要后续任务添加异常受试者自动标记
```
