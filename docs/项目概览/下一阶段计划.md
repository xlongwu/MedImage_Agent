# MedImage Agent 下一阶段详细方案

> 版本路线：v0.2–v0.5  
> 主题：Hermes 增量改进 → 真实 SPM / DPABI / GPU 接入 → LLM 辅助助手层  
> 核心原则：保持确定性医学影像 pipeline 作为执行核心，LLM 和 Hermes-style 能力只作为外层增强，不让 LLM 直接决定或执行医学影像数据修改。

---

## 1. 当前阶段判断

当前 MedImage Agent 的基础框架已经完成，且 Hermes Agent 对标审计结果表明：

- MedImage Agent 不需要重构为通用 LLM 对话式 Agent。
- 当前“确定性医学影像流水线引擎 + agent 化辅助层”的路线是合理的。
- Hermes 的分层架构、规划-执行-审查、工具权限、记忆、错误知识库、安全边界等模式已经被较好吸收。
- 后续应做增量增强，而不是大规模重构。

接下来的计划应分为三条主线：

1. **Hermes 增量改进**：让系统具备更强的运行记忆、错误学习、洞察分析和异步审查能力。
2. **真实 SPM / DPABI / GPU 接入**：从 contract-only 逐步进入受控真实后端执行。
3. **LLM 辅助助手层**：让 LLM 作为 protocol advisor、error advisor、QC report advisor，而不是执行器。

---

## 2. 总体架构原则

### 2.1 确定性执行核心不变

MedImage Agent 的执行核心继续保持：

```text
Pipeline YAML
→ Node planning
→ Tool registry
→ Permission / approval gate
→ Deterministic execution
→ QC
→ Report
→ Run history
```

这个核心不应被 LLM 替代。LLM 不应直接决定是否执行真实医学影像处理。

### 2.2 LLM 只能作为顾问层

禁止模式：

```text
LLM 自主选择工具
→ LLM 自主决定参数
→ LLM 自主执行真实影像处理
→ LLM 自主修改或删除文件
```

允许模式：

```text
LLM 阅读 metadata / QC / error / docs
→ 生成解释、建议、候选参数、修复计划
→ 用户确认
→ 确定性 pipeline 执行
```

### 2.3 真实后端必须逐级开放

SPM / DPABI / GPU 的能力开放顺序应为：

```text
contract-only
→ dry-run
→ synthetic data execution
→ sandbox real-data read-only inspection
→ explicit approved single-subject execution
→ controlled batch execution
```

任何真实执行都必须满足：

- 有 approval gate；
- 有 input/output 白名单；
- 有日志；
- 有 run summary；
- 有失败恢复策略；
- 不修改 rawdata；
- 不删除文件。

---

## 3. 阶段路线图

| 阶段 | 主题 | 目标 | 建议版本 |
|---|---|---|---|
| Phase A | v0.1 封版验证 | 干净环境跑通、生成 release notes | v0.1.0 |
| Phase B | Hermes 增量改进 | SessionDB、Insights、Error Intelligence、MemoryProvider、Async Review | v0.2.0 |
| Phase C | 真实 SPM 联调 | MATLAB/SPM 环境真实跑通单节点和链式 pipeline | v0.3.0-alpha |
| Phase D | DPABI wrapper 原型 | 接入 DPABI 单函数，不接 DPARSF 全流程 | v0.3.0-beta |
| Phase E | GPU backend 原型 | ALFF/ReHo/FC 的可选 GPU backend | v0.3.0 |
| Phase F | LLM Advisor Layer | 协议建议、错误解释、报告叙述、文档问答 | v0.4.0 |
| Phase G | 真实数据沙盒 | 只读真实数据检查、协议生成、手动审批执行 | v0.5.0 |

# Phase B：Hermes 增量改进

这一阶段是最适合立即开展的方向。它不会改变 MedImage Agent 的确定性 pipeline 核心，而是补强 Hermes Agent 中对 MedImage 有价值的部分：长期记忆、运行检索、错误智能、洞察分析和后台审查。

## B.1 SessionDB + FTS5：可查询运行记忆

### 目标

把当前分散的 JSON / JSONL / run history 记录汇总进 SQLite 数据库，支持跨运行搜索。

### 当前问题

现有状态主要存储在：

```text
work/pipeline_runs/*/summary.json
demo_runs/*/quickstart_demo_summary.json
reports/run_history/run_history_index.json
memory/RUN_HISTORY.jsonl
```

这些文件可读，但不适合查询：

```text
最近 10 次运行中哪些 subject 失败？
哪个 node 最常失败？
normalization 失败的错误有哪些？
某个 subject 的历史处理状态是什么？
```

### 建议新增文件

```text
backend/app/memory/session_db.py
backend/app/tools/session_indexer.py
backend/app/tools/session_query.py
examples/pipeline_session_index.yaml
tests/unit/test_session_db.py
frontend/src/components/SessionMemoryBrowserPanel.tsx
```

SQLite 路径：

```text
memory/sessions/archive.sqlite
```

### 核心表设计

```sql
runs(
  run_id TEXT PRIMARY KEY,
  pipeline_id TEXT,
  status TEXT,
  started_at TEXT,
  finished_at TEXT,
  source_path TEXT
)

nodes(
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  run_id TEXT,
  node_id TEXT,
  subject_id TEXT,
  status TEXT,
  ok INTEGER,
  duration_seconds REAL,
  outputs_json TEXT,
  warnings_json TEXT,
  errors_json TEXT
)

errors(
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  run_id TEXT,
  node_id TEXT,
  subject_id TEXT,
  category TEXT,
  message TEXT,
  retryable INTEGER,
  created_at TEXT
)

documents(
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  record_id TEXT,
  record_type TEXT,
  title TEXT,
  body TEXT
)
```

FTS5：

```sql
CREATE VIRTUAL TABLE documents_fts USING fts5(
  record_id,
  record_type,
  title,
  body
);
```

### API

```text

GET  /api/sessions/query?q=...
```

### 验收标准

- 能从已有 run_history / pipeline_runs / demo_runs 建库；
- 支持关键词搜索；
- 支持按 node_id / subject_id / status 过滤；
- 不修改原始历史文件；
- 只写 memory/sessions/archive.sqlite。

## B.3 Error Intelligence：结构化错误知识库

### 目标

将 ERROR_KB 从简单字符串匹配升级为结构化错误诊断系统。

### 建议 ERROR_KB schema

```yaml
version: "0.2.0"

categories:
  matlab_missing:
    severity: high
    retryable: false
    patterns:
      - "matlab: command not found"
      - "No MATLAB executable"
    likely_causes:
      - "MATLAB is not installed or not on PATH"
    suggested_fixes:
      - "Install MATLAB"
      - "Configure MATLAB executable path"
    affected_backends:
      - matlab
      - spm

  spm_path_error:
    severity: high
    retryable: false
    patterns:
      - "Undefined function or variable 'spm'"
      - "spm not found"
    suggested_fixes:
      - "Check SPM path"
      - "Run environment check"
```

### 建议新增模块

```text
backend/app/tools/error_classifier.py
backend/app/tools/error_kb_validator.py
tests/unit/test_error_classifier.py
```

### 分类字段

```text
category
severity
retryable
human_action_required
suggested_fix
affected_backend
safe_to_retry
recommended_next_step
```

### API

```text
POST /api/errors/classify
GET  /api/errors/kb
POST /api/errors/kb/validate
```

### 验收标准

- 支持至少 15 类错误；
- 能对 pipeline error 自动分类；
- 分类结果进入 SessionDB；
- release readiness 检查 ERROR_KB schema；
- 不自动执行修复，只给建议。

# Phase E：GPU backend 原型

GPU 应作为可选加速后端，不应成为默认依赖。

## E.1 优先实现顺序

```text
1. ALFF / fALFF GPU backend
2. FC matrix GPU backend
3. ReHo GPU backend
```

原因：

- ALFF/fALFF FFT 更适合 GPU；
- FC 可通过矩阵乘法加速；
- ReHo 涉及局部排名，GPU 实现复杂度更高。

## E.2 后端策略

支持：

```text
cpu_numpy
gpu_cupy
gpu_torch
matlab_gpuarray
```

默认：

```text
cpu_numpy
```

GPU 运行必须显式开启：

```yaml
params:
  backend: gpu_cupy
  approved_gpu: true
```

## E.3 GPU capability check

新增：

```text
backend/app/tools/gpu_capability.py
```

输出：

```text
work/gpu/gpu_capability.json
```

检查：

```text
CUDA 是否可用
CuPy 是否可用
Torch CUDA 是否可用
GPU name
GPU memory
driver info
```

## E.4 验收标准

- 无 GPU 环境测试仍通过；
- GPU backend 不影响 CPU backend；
- GPU 结果与 CPU 结果误差在阈值内；
- 记录 device info；
- explicit approval；
- 不隐式执行 GPU。

## F.3 LLM 安全策略

每个 advisor 输出必须包含：

```json

  "advice_only": true,
  "requires_human_confirmation": true,
  "will_execute_pipeline": false,
  "will_modify_data": false,
  "clinical_conclusion": false

```

禁止：

```text

LLM 直接修改 NIfTI
LLM 直接改 YAML 并执行
LLM 直接删除文件
LLM 直接调用 DPABI/SPM/GPU
```

# 6. 风险与控制策略

## 6.1 LLM 越权执行

控制：

- advisor 与 executor 物理隔离；
- advisor 不 import pipeline_executor；
- advisor output 强制 safety flags；
- 所有执行仍走 pipeline approval gate。

## 6.2 真实数据被误修改

控制：

- rawdata 只读；
- path_safety 白名单；
- output 必须在 derivatives / reports / work / exports；
- execution audit log；
- real-data mode 默认 readonly。

## 6.3 DPABI 全流程不可控

控制：

- 不接 DPARSF_run；
- 先做 single-function wrapper；
- dry-run 优先；
- explicit approved=true；
- MATLAB script snapshot；
- stdout/stderr log。

## 6.4 GPU 环境差异大

控制：

- GPU 可选；
- CPU fallback；
- device capability check；
- 数值误差阈值测试；
- 不把 GPU 设为默认 backend。

## 6.5 系统变得过度复杂

控制：

- 每个新模块必须有 spec、tool、API、frontend、test、docs；
- 不通过“大重构”解决小问题；
- 优先可审计、可回滚的增量 PR。
