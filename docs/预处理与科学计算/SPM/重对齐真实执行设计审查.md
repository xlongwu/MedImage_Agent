## 4. Proposed Execution Architecture

Future execution flow for `spm_realign_subject`:

```text
1.  Reviewed plan exists (reviewed_plan_id, project_context match).
2.  Plan validates (validate_plan → ok=true).
3.  Approval Gate passes (all 6 external-tool fields present).
4.  Audit record is persisted (build_review_audit_record).
5.  Environment health is checked (MATLAB/SPM paths valid).
6.  Dry-run manifest is generated (build_spm_realign_dry_run).
7.  Output conflicts are checked (would_overwrite → blocked).
8.  Command template ID is resolved (spm12_realign_estwrite_v1).
9.  MATLAB batch file (.m) is written to run work directory.
10. MATLAB is invoked via subprocess with safe command template.
11. stdout/stderr are captured to log files.
12. Expected outputs are verified (all predicted paths exist + non-zero).
13. Provenance JSON is written.
14. Node state is updated (write_node_state).
15. Run summary is updated (write_pipeline_summary).
16. Artifacts become previewable through existing artifact discovery.
17. Motion QC readiness / metrics draft can consume rp_*.txt.
```

**Fail-closed**: any failure at any stage blocks execution and records the
specific failure reason in node state, run summary, and warnings.

## 5. MATLAB Invocation Strategy

### Option A: `matlab -batch "<commands>"`

```python
subprocess.run(
    [matlab_command, "-batch", "spm; spm_jobman('run', matlabbatch); exit"],
    capture_output=True, text=True, timeout=600,
)
```

**Pros**: Simple, no file I/O for the script, direct stdout/stderr capture.
**Cons**: Command injection risk if params are interpolated; Windows path
quoting is fragile; difficult to reproducibility-debug.

### Option B: Generate `.m` batch file, call wrapper function

```python
batch_path = work_dir / f"{run_id}_{subject}.m"
batch_path.write_text(batch_content, encoding="utf-8")
subprocess.run(
    [matlab_command, "-batch", f"run('{batch_path}'); exit"],
    capture_output=True, text=True, timeout=600,
)
```

**Pros**: Batch file is inspectable, checksum-able, provenance-tracked.
Reproducible debugging. No param interpolation in command string.
**Cons**: One extra file write (acceptable — already under run work directory).

### Recommendation

**Option B** is recommended.  The batch `.m` file should be generated from a
versioned template (`spm12_realign_estwrite_v1`), written only under the run
work directory, and its SHA-256 checksum recorded in provenance.  No
user-provided MATLAB code.  No shell string-building from params.

## 6. SPM Batch Generation Strategy

Future batch generation must:

- Only use params validated by `validate_spm_realign_params()`.
- Only use BOLD inputs discovered by the dry-run manifest.
- Accept **no** user-provided MATLAB code or script fragments.
- Use the versioned command template ID (`spm12_realign_estwrite_v1`).
- Write the `.m` file only under `<work_dir>/batch/<run_id>/`.
- Never write to rawdata or outside the project run scope.
- Record the batch content SHA-256 in provenance.
- Follow the MATLAB batch structure already previewed in
  `spm_realign_wrapper_skeleton.py._build_matlab_batch_preview()`.

## 7. Output Layout Decision

### Proposed layout

```text
outputs/derivatives/spm_realign/<project_id>/<run_id>/
├── sub-XXX/
│   └── func/
│       ├── r<sub>_bold.nii.gz          (realigned BOLD)
│       ├── mean<sub>_bold.nii.gz        (mean/reference)
│       └── rp_<sub>_bold.txt            (motion parameters)
├── logs/
│   ├── <sub>_spm_realign_stdout.log
│   └── <sub>_spm_realign_stderr.log
├── provenance/
│   └── <sub>_spm_realign_provenance.json
└── state/
    └── <sub>_spm_realign_node_state.json
```

### Discussion

- **Run-scoped**: each execution gets its own `<run_id>` subdirectory, avoiding
  overwrite conflicts with previous runs.
- **Project-scoped root**: `outputs/derivatives/spm_realign/<project_id>/`
  keeps all runs for one project together.
- **BIDS-compatible subject/session nesting**: facilitates future BIDS
  derivatives compliance.
- **Never inside rawdata**: the output root is under `outputs/derivatives/`,
  not under the raw BIDS directory.

## 10. Failure Handling Policy

| Failure | Status | Next Action |
|---|---|---|
| MATLAB missing | BLOCKED | Verify MATLAB path in desktop config |
| SPM missing | BLOCKED | Verify SPM path; check environment health |
| MATLAB timeout | FAILED | Increase timeout or check input size |
| Non-zero return code | FAILED | Inspect stderr log; check MATLAB batch |
| Output missing | FAILED | Inspect logs, verify batch content |
| Partial output | FAILED | Mark node FAILED; report missing files |
| Output conflict (overwrite_policy=fail_if_exists) | BLOCKED | Clear previous outputs or use new run_id |
| Permission error | BLOCKED | Check output directory permissions |
| Malformed batch | BLOCKED | Fix command template; re-validate params |
| Provenance write failure | WARNING | Execution continues but provenance incomplete |
| Audit write failure | BLOCKED | Fix audit directory permissions |
| Log write failure | WARNING | Execution continues but logs not captured |
| User cancellation | KILLED | Mark node KILLED; partial outputs may exist |
| Process killed (OOM/signal) | FAILED | Record signal; preserve partial outputs |

## 15. Rollback and Disable Strategy

If problems occur with real SPM execution, disable it by:

1. Removing `spm_realign_subject` from safe allowlist.
2. Unsetting `MEDIMAGE_MATLAB_ENABLED` environment variable.
3. Hiding the execute action for SPM nodes in the frontend (or keeping it
   disabled with the existing gating logic).
4. Keeping dry-run manifest and wrapper skeleton previews fully functional.
5. Preserving old run artifacts — never deleting outputs automatically.
6. Recording the disable event in an audit record.

## 17. Go / No-Go Decision

**Decision: NO-GO for real MATLAB/SPM execution in the current phase.**

Rationale:

- The non-executing preparation chain is complete and tested.
- MATLAB invocation, batch generation, output verification, and failure
  handling are not yet implemented or tested.
- No synthetic or external BIDS smoke test exists for real execution.

**Decision: GO for the following preparatory tasks:**

1. Command template pure-function unit tests (`test_spm_realign_command_template.py`)
2. SPM execution contract schema and tests (`test_spm_realign_execution_contract.py`)
3. Synthetic smoke design behind explicit environment flag (test plan only,
   no implementation required yet)
4. Output/provenance schema alignment

## 18. Immediate Next Tasks

Recommended next safe tasks (in order):

1. **Command template pure-function tests** — generate batch content from
   dry-run manifest and params; validate structure, no shell injection, stable
   SHA-256.
2. **SPM execution contract schema** — define Pydantic models for the
   execution payload (batch path, command, timeout, output manifest).
3. **Synthetic smoke design** — document the test fixture and env-gate
   pattern for local MATLAB/SPM smoke (no implementation yet).
4. **Output/provenance schema alignment** — ensure the proposed derivatives
   layout matches what artifact discovery and motion metrics draft expect.

Only after these pass should implementation of actual MATLAB invocation begin.
