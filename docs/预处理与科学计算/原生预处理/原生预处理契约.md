# Native Preprocessing Contract

Status: Phase 01 contract baseline with current implementation note.

This contract originally defined the boundary for the Python-native rs-fMRI
preprocessing backend before implementation. It remains the safety and
truthfulness contract for the implemented native runtime surfaces.

## Current Implementation Note

As of 2026-06-28, the native full preprocessing API, node registry entries,
Tool Catalog metadata, reviewed preprocessing delegation, and frontend native
full workflow are implemented as current runtime surfaces. This document still
preserves the original contract language, but it should now be read together
with `docs/预处理与科学计算/原生预处理/阶段矩阵.md`,
`docs/预处理与科学计算/原生预处理/验证报告.md`, and `docs/项目概览/能力矩阵.md`
for current status.

The native default path is not an SPM/DPABI-equivalent path. Current spatial
stages remain deliberately limited: realignment is a simplified native
baseline, coregistration is affine/simple, segmentation is intensity based, and
normalization is affine-only. External SPM/DPABI execution remains explicit,
approval-gated, environment-gated, audited, and disabled by default.

## Scope

The native preprocessing backend is a project-internal Python implementation
for rs-fMRI preprocessing stages. It must produce real numerical artifacts for
computed stages and must not report dry-run, metadata-only, scaffold, or preview
outputs as computed scientific completion.

## Runtime Prohibitions

The native backend must not:

- call MATLAB;
- call SPM;
- call DPABI or DPARSF;
- import SPM or DPABI code as runtime Python modules;
- execute any `third_party/**/*.m` file;
- shell out through unrestricted commands;
- weaken Approval Gate, audit logging, path validation, or raw-data protection;
- make clinical diagnosis or treatment claims.

Forbidden native-runtime examples:

```text
matlab -batch
matlab -r
spm_jobman
DPARSFA_run
DPABI_run
```

External SPM/DPABI backends may remain available only as explicit,
approval-gated, audited, environment-gated reference/execution paths. They are
not the native backend.

Numerical algorithms belong in `native_preproc/stages/` or
`native_preproc/core/`. Routes must not implement numerical algorithms.

## Capability Truth Levels

Native code and documentation must use truthful capability labels.

| Capability | Meaning |
| --- | --- |
| `unavailable` | No implementation exists |
| `scaffolded` | Interface exists but no valid numerical artifact is produced |
| `metadata_only` | Metadata/planning is produced without the declared numerical artifact |
| `computed` | Declared numerical artifact was created and can be reloaded |
| `numerically_implemented` | Native numerical implementation exists with focused synthetic tests |
| `simplified` | A deliberately simplified implementation exists and is labeled as such |
| `affine_only` | Spatial normalization is limited to affine behavior |
| `validated` | Computation passed defined numerical validation |
| `reference_validated` | Computation passed reference/golden comparison criteria |

Initial native implementations must not jump directly to `reference_validated`
or release-ready language. Reference validation requires explicit golden or
independent reference comparison.

## Stage Status Semantics

Allowed native stage statuses are:

```text
not_started
planned
running
succeeded
partial
warning
failed
blocked
metadata_only
simplified
reference_validated
```

Rules:

- `metadata_only` cannot claim `computed`, `numerically_implemented`,
  `validated`, or `reference_validated` capability.
- `succeeded` requires a real numerical artifact for computational stages.
- `simplified` must describe the simplification and must not be described as
  SPM/DPABI equivalent.
- `reference_validated` is allowed only after documented reference validation.
- Failed, partial, blocked, or missing-output stages must not be converted into
  success by report-generation code.

## Artifact Integrity

A computational stage is not complete unless its declared artifact:

- exists;
- is non-empty;
- contains the numerical result;
- can be reopened by the relevant loader;
- has the expected shape and dtype;
- is registered in the run artifact registry;
- records source artifact lineage;
- records relevant parameters and warnings;
- has failure handling for missing or partial writes.

Metadata sidecars supplement numerical artifacts. They do not replace them.

Metadata/report stages are different from computational stages. The stages
`input_validation`, `bids_sidecar_validation`, `subject_qc`, `group_summary`,
`validation_report`, and `final_report` may complete by writing metadata,
manifests, QC summaries, validation reports, or final reports. They must not be
required to emit NIfTI or NumPy numerical artifacts, and they must not be used
as substitutes for missing numerical outputs from core computation stages.

## Provenance Minimum

Where applicable, provenance must include:

- algorithm ID and version;
- implementation kind;
- input artifact IDs and checksums;
- subject/session identifiers;
- parameters;
- backend;
- precision and dtype;
- random seed when used;
- package versions;
- warnings;
- output checksums;
- creation timestamp.

Portable provenance should avoid private machine-specific absolute paths unless
the local runtime state explicitly requires them.

## QC Minimum

Every computational stage should report:

- QC status;
- measured metrics;
- thresholds;
- warnings;
- errors;
- relevant artifact paths or artifact IDs.

QC cannot turn a missing numerical artifact into a successful stage.

## Validation Expectations

Minimum validation for native scientific stages:

- synthetic input tests;
- shape/dtype checks;
- zero/constant-signal or insufficient-input edge cases where applicable;
- reload tests for persisted artifacts;
- provenance tests;
- artifact registry tests;
- status truthfulness tests.

Golden/reference validation is a later step and requires approved reference
outputs and documented tolerance criteria.
