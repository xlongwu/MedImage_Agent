# Native Preprocessing Validation Report

Current as of 2026-06-28.

This document records the phase 07 validation posture for the Python-native
rs-fMRI preprocessing backend. It is a validation and readiness summary, not a
claim that the native backend is SPM/DPABI equivalent.

## Scope

Validated in this phase:

- Synthetic BIDS-to-FC native full run.
- Post-DICOM-conversion handoff into native full preprocessing, with rawdata
  preserved read-only.
- Artifact integrity for every emitted NIfTI, NumPy matrix, TSV, JSON, and
  report artifact in the native full run manifest.
- Validation report and final report consistency with the run manifest.
- Truthful status behavior: missing reference evidence does not upgrade stages
  to `reference_validated`.
- A reusable numeric reference comparison framework for approved future
  golden/reference fixtures.

Not validated in this phase:

- External SPM/DPABI/MATLAB numerical equivalence.
- GUI workflow execution.
- GPU execution.
- Packaged desktop launch.
- Cross-platform behavior outside the local Windows validation environment.
- Real private research DICOM/BIDS/NIfTI datasets.

## DICOM Conversion Boundary

The native full runner does not run DICOM conversion internally. The
`dicom_to_nifti` stage in the native graph remains a handoff/skipped boundary:
conversion-domain services register converted BIDS/NIfTI outputs and write a
preprocessing input registry, then native full preprocessing can resolve BOLD,
sidecar, T1w, and optional atlas inputs from that registry. Therefore current
evidence is "conversion-domain output to native FC" rather than "native runner
performs one-click DICOM conversion to FC".

Rawdata checksum/read-only guarantees belong to the conversion domain and the
handoff registry tests; native preprocessing itself consumes registered
converted inputs and must not modify rawdata.

## Runtime Report Contract

Native full execution writes:

- `native_full_run_manifest.json`
- `native_preproc_validation_report.json`
- `native_preproc_final_report.json`

Metadata/report stages (`input_validation`, `bids_sidecar_validation`,
`subject_qc`, `group_summary`, `validation_report`, and `final_report`) emit
metadata, QC, validation, or report artifacts. They are not expected to emit
NIfTI/NumPy numerical artifacts and do not replace missing numerical outputs
from computational stages.

The validation report includes:

- `artifact_validation`: existence, non-empty, reload, shape, dtype, and
  checksum-backed artifact checks.
- `truthfulness`: status/capability checks, including prevention of
  `reference_validated` claims without passed comparison evidence.
- `safety_checks`: rawdata read-only, no external tools, no MATLAB/SPM/DPABI,
  no runtime `third_party` use, research-use-only, and no clinical-use claims.
- `reference_validation`: `not_provided` when no approved reference artifact is
  supplied.
- `limitations`: explicit local validation boundaries.

## Reference Validation Policy

The helper module
`src/backend/app/native_preproc/orchestrator/golden_reference.py` compares
candidate arrays or persisted artifacts against approved references using:

- shape consistency;
- MAE;
- RMSE;
- max absolute error;
- correlation threshold when requested;
- Dice threshold when requested.

Reference validation is opt-in. A stage may not claim `reference_validated`
unless a comparison result for that stage is present and passed. If no approved
SPM/DPABI or independent reference fixture is supplied, the validation report
records reference status as `not_provided`.

## Remaining Risks

- Golden reference data, tolerance, provenance, license, and CI cost still need
  maintainer approval before any stage can be upgraded to
  `reference_validated`.
- Simplified stages remain simplified: realignment is translation-only,
  coregistration/normalization are affine/simple baselines, and segmentation is
  intensity-based.
- The native full runner validates synthetic small-volume data here; large
  real-data performance and numerical robustness remain future validation work.
- The local backend release suite is passing, but GUI workflow, GPU, packaged
  desktop, cross-platform, real-data, and external reference validations remain
  separate evidence streams.
