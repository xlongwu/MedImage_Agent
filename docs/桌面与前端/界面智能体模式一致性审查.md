## 3. Canonical Response Field Set

All mock adapter route responses now include these fields (where applicable):

```json
{
  "ok": true|false,
  "status": "MODEL_ACTION_MAPPED",
  "fixture_id": "...",
  "model_output_id": "...",
  "adapter_decision": "mapped|rejected",
  "adapter_status": "NORMALIZED_ACTION_READY|null",
  "adapter_rejection_reason": "...|null",
  "submitted_to_guard": true|false,
  "guard_status": "GUI_GUARD_OK|GUI_GUARD_*|SESSION_NOT_FOUND|null",
  "guard_error_code": "...|null",
  "audit_id": "audit_...|null",
  "normalized_action_type": "record_observation|null",
  "provider_call_allowed": false,
  "provider_call_allowed_by_adapter": false,
  "provider_call_allowed_by_guard": true|false,
  "desktop_touched": false,
  "screenshot_captured": false,
  "clipboard_accessed": false,
  "mouse_used": false,
  "keyboard_used": false
}
```

### `provider_call_allowed` Field Semantics

| Field | Used In | Always | Set By |
|-------|---------|:---:|------|
| `provider_call_allowed` | Rejected, fixture-not-found, session-required | `false` | Mock route |
| `provider_call_allowed_by_adapter` | Mapped, dry-run, guard-blocked | `false` | Mock route |
| `provider_call_allowed_by_guard` | Mapped, dry-run, guard-blocked | `true` only on success | Guard step route |

**Design rationale:** Rejection/error paths have no guard involvement, so `provider_call_allowed` suffices. Mapped paths have both adapter and guard roles, so the distinction is explicit. This is intentional, not an inconsistency.

## 6. Accepted Remaining Inconsistencies

The following are intentional design choices, not bugs:

1. **`SESSION_NOT_FOUND` prefix**: This is a route-level status, not a guard error code. It reflects a session lookup failure in the mock route, not a guard policy decision.

2. **`BLOCKED` fallback**: Used only when `HTTPException.detail` is not a string. In practice, all guard exceptions return string details, so this path is never reached in normal operation.

3. **`provider_call_allowed` naming**: Rejection paths use `provider_call_allowed=false` because there is no adapter/guard distinction — the provider was never involved. Mapped paths use `by_adapter`/`by_guard` to explicitly show authority boundaries.

4. **`audit_id` null for guard-blocked**: The guard-blocked path in the mock route catches `HTTPException` and does not have access to the guard's audit record. This could be enhanced in a future task to surface blocked audit IDs.
