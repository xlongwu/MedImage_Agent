## Task Format

Each task preserves structure from the spec:

```markdown
- [ ] **T{batch}.{num}: {Title}** | {OPERATION} {path}
  - Objective: {from spec - what this task achieves}
  - DoD:
    - {requirement 1}
    - {requirement 2}
    - {requirement N}
  - Evidence: {from spec - file:line or pattern reference}
  - Verify: `{behavioral verification command}`
  - Mitigates: {H-ID list or "none"}
  - Mitigation: {from spec - how to address the risks}
```

### Field Requirements

| Field | Required | Source |
|-------|----------|--------|
| Checkbox | Yes | Generated (`- [ ]` or `- [x]`) |
| Task ID | Yes | Generated (`T{batch}.{num}`) |
| Title | Yes | From spec |
| Operation | Yes | From spec (`CREATE` or `MODIFY`) |
| Path | Yes | From spec |
| Objective | Yes | Copy from spec |
| DoD | Yes | Copy from spec (multi-line OK) |
| Evidence | Yes | Copy from spec |
| Verify | Yes | Generated behavioral command |
| Mitigates | Yes | From spec |
| Mitigation | Yes | Copy from spec |

### Verification Command Guidelines

| Task Type | Verification Approach |
|-----------|----------------------|
| Has test file | Reference test: `npm test -- --testPathPattern="..."` |
| Complex logic | Inline behavioral: `python -c "..."` or `npx ts-node -e "..."` |
| Simple file | Structural: `test -f {path}` |
| Config/data | Schema validation or structural |

**See**: `templates/verification-patterns.md` for language-specific patterns.

---

## Verification Principles

The verification command must **robustly evaluate** whether DoD is achieved.

### Key Principle

**Behavioral over structural**: If DoD describes behavior, the verification should test behavior.

- DoD: "Class instantiates with id parameter" → Verify: run code, check `obj.id == expected`
- DoD: "File exports function" → Verify: import the function, not grep for text
- DoD: "Test passes" → Verify: run the actual test

### Verification Command Requirements

1. **Exit 0 = DoD achieved** - Command must exit 0 only when ALL DoD items are satisfied
2. **Deterministic** - Same code produces same result
3. **Self-contained** - No external setup beyond the code being verified
4. **Appropriate for DoD** - If DoD is behavioral, verification must test behavior

### When Tests Exist

If the project has tests that cover the DoD, reference them directly:
```
Verify: `{test_runner} {test_file}::{test_name}`
```

### Execute Agent Freedom

The execute agent has full agency to:
- Use Serena for semantic symbol verification
- Read files directly to verify content
- Run code to test behavior
- Use any appropriate method to confirm DoD

The verification command is the **final gate check**, not the only tool execute can use.

## Batch Gate Format

```markdown
**Batch {N} Gate**:
- [ ] All tasks above checked
- [ ] Type check: `tsc --noEmit` exits 0
- [ ] Tests: `npm test -- --testPathPattern="{pattern}"` passes
```

### Test Pattern Examples

| Batch | Pattern |
|-------|---------|
| Types | `types` or `src/types` |
| Domain | `domain` |
| Infrastructure | `infrastructure\|infra` |
| Application | `application\|app` |
| Workers | `workers\|worker` |

---

## Status Values

### Frontmatter `status`
- `IN_PROGRESS` - Execution ongoing
- `COMPLETE` - All batches passed
- `BLOCKED` - Failed verification, needs intervention

### Task Checkbox
- `- [ ]` - Not started or in progress
- `- [x]` - Complete and verified

### Batch Gate
- All unchecked `- [ ]` - Batch not complete
- All checked `- [x]` - Batch gate passed, can proceed to next
