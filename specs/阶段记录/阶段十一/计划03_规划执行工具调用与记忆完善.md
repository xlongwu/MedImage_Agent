# 计划 03：规划、执行、工具调用与记忆完善

> 状态：Proposed。任务模式：Feature Bundle + Architecture / Refactor。  
> 目标：补齐现有 Agent 四个基础能力的可靠性和可验证性，使它们可作为 Harness 的稳定底座。

## 一页决策

不新建第二条执行路径，也不把模型变成权限主体。规划输出、工具元数据、记忆影响和执行证据必须有稳定 schema、hash、错误码和回归测试；模型或记忆不可用时，系统停止或明确回退，绝不悄悄换一个计划执行。

本计划先完成现有单 Agent 基础，再实施计划 02。真实 LLM 和长期记忆仍默认关闭，启用必须由安装级配置、项目级 consent 和健康检查共同决定。

## 范围、非目标与验收

| 能力 | 本计划完成后的最低标准 |
|---|---|
| 规划 | 规则 planner 与真实 provider 使用同一 Plan/Goal Contract；输入、输出、模型和 prompt 版本可追溯。 |
| 执行 | Approval Summary、ticket、gateway、run 状态与 artifact 形成单一、可重放的证据链。 |
| 工具调用 | 每个可规划/可执行 node 均有统一的输入输出合同、风险和审批元数据；未知 node 永远拒绝。 |
| 记忆 | 独立、项目隔离、默认关闭；只以 typed context 影响允许的低风险规划字段，快照绑定 Reviewed Plan。 |

不做：自动审批、模型直连 runner、任意 shell/MCP 工具、跨项目 profile、把科学建议自动写入参数、把 memory 当作当前事实或执行权限。

完成条件：

- [ ] 未配置 LLM、模型超时、模型 schema 错误和记忆数据库故障都有确定的结构化结果与不执行证明。
- [ ] 计划、审批、ticket、gateway、artifact 和 memory context 的 hash 能从一个 run 反查，并能拒绝篡改或过期输入。
- [ ] 注册表、Tool Catalog、Node Contract 和审批摘要对同一 node 的风险与输入输出描述一致。
- [ ] 启用和关闭真实 LLM/记忆后，plan-only、审批顺序、rawdata 只读、重启恢复和前端投影仍通过回归。

## 锁定合同

### 1. 规划

新增统一的 `PlannerInvocation` 与 `PlannerEvidence`，保存到 Reviewed Plan 的 provenance：

```text
PlannerInvocation: provider_id, model_id, prompt_template_version,
input_schema_version, input_hash, started_at, timeout_ms
PlannerEvidence: invocation_id, output_hash, validation_codes,
fallback_used, failure_code, redacted_summary
```

规则 planner 的 `provider_id="rule_based"`，真实 provider 的 `provider_id="openai_compatible"`；两者都只能返回同一个 Pydantic Plan schema。真实 provider 的 JSON 无法通过 validator 时，最多一次同输入的格式修复；仍失败则返回 `PLANNER_OUTPUT_INVALID`，不自动换成内容不同的规则计划。

### 2. 执行

每个 execution attempt 必须保留以下不可变关系：

```text
ReviewedPlan(plan_hash, memory_context_hash)
 -> ApprovalSummary(summary_hash, plan_hash)
 -> ExecutionTicket(ticket_id, summary_hash, expiry, scope_hash)
 -> GatewayDispatch(dispatch_id, ticket_id, allowlist_hash)
 -> Run(run_id, dispatch_id)
 -> Artifact(run_id, input_hashes, parameter_hash, checksum)
```

任何 hash 不匹配、ticket 过期、scope/allowlist 变化、artifact 不可重载或 post-approval dry-run 失败，都必须阻断 dispatch 并写结构化审计。相同 command ID 只能复放已持久化结果，不能重复 dispatch。

### 3. 工具

`NodeContract` 是 node 输入/输出的唯一 schema；Tool Catalog 只补充用户可见说明、风险、审批和 write root。每次应用启动和 CI 都运行 registry consistency check：每个可执行 node 恰有一个 NodeContract 和一个 Tool Catalog item；backend、输入类型、输出类型、requires_approval、manual_required、write roots 不一致即启动失败。

### 4. 记忆

启用条件固定为：安装级 generation/use 配置为真、项目 consent 为真、memory DB migration/health/outbox preflight 通过。planner 只能经 `MemoryContextService` 获取 typed context；科学参数只形成待确认 decision，永不直接写入 plan 参数；执行时不重新检索 memory。

## 风险与防护

| 风险 | 防护 | 验证 |
|---|---|---|
| 真实 LLM 产生不合法计划 | schema、validator、Goal Contract、一次格式修复上限；失败不执行。 | provider fixture 与 plan-only 回归。 |
| 元数据说允许、runner 实际不允许 | Registry/Contract/Catalog 三方一致性检查，启动和 CI fail closed。 | 缺失/冲突矩阵测试。 |
| 记忆污染或跨项目泄漏 | typed allowlist、双 gate、project 条件、hash、科学参数二次确认。 | PHI/secret/injection/cross-project tests。 |
| hash 链断裂或重复 dispatch | 每层绑定前一层 hash/ID；command idempotency；gateway 二次校验。 | tamper、expiry、replay tests。 |
| 为了可用性绕过默认关闭 | flag/consent/health 任一不满足即 disabled；UI 显示原因。 | config 与 UI tests。 |

## 文档更新与最终审查

实现完成后必须同步 `docs/架构与决策/系统架构.md`、`docs/安全与审批/安全边界.md`、`docs/规划与运行时/`、`docs/项目概览/能力矩阵.md`（仅真实能力变化）、`README.md`、`README_CN.md`、`.env.example` 和 `PROJECT_STATE.md`（仅验证状态变化）。`AGENTS.md` 仅在发现可复发且现有规则未覆盖的新风险时更新。

## 评审结论

计划 03 不追求“更自主”，而是让四个已有能力变得可证明、可恢复、可解释。完成它之后，计划 02 可以在稳定的 provider、工具合同、执行证据和记忆边界上实现 Harness，而不会复制或绕过现有安全链。
